# Experimental assumptions

## Experimental and engineering decisions

1. **Scope:** compare measured screeners with published aggregates, with sharks as the primary task and animal/leather as manually reviewed replications. This supersedes the earlier sharks-only scope. No training, pseudo-labelling of the pool, threshold selection or author outreach.
3. **Gold label semantics:** when no task mapping or explicit override is configured, infer the positive numeric value only when all populated recognised `relevant` values uniquely support one mapping. Otherwise fail. Local validation has 274 populated text labels, all supporting 1=positive, plus 225 blanks. A user-supplied `--positive-label` is an explicit mapping override after local review; it never repairs individual labels.
4. **Missing text labels:** blank `relevant` is unannotated, not a negative. The numeric column is the complete evaluation target. Missing values and disagreements are reported separately. Unknown textual labels fail even with an override.
5. **Pool labels:** observed 0/1 counts do not establish source or accuracy. The pool's label provenance remains unknown; the current study does not use it as evaluation or training data.
6. **Inspection:** fossil/replica spot-checks match title keywords, include every match and retain original gold labels. Keyword matches are not expert adjudications. Duplicate titles are exact strings, not near-duplicates. No deduplication or relabelling alters the test denominator.
7. **Identity:** use advert_id, then id, then CSV row number. Require unique IDs, nonempty titles (or explicitly selected combined text), well-formed CSV rows and 0/1 labels. An unchanged ID with changed allowlisted text fails cache validation; a new source/config namespace must be intentional. Row-number IDs are order-dependent.
8. **Fields:** title by default; description may be added explicitly. Alternatively, `--combined-text` explicitly selects only `title_and_desc`, which may contain both title and description. Do not use clean_title, training_text, descriptions, image paths, seller, location, prices or URLs. Scorer input dataclasses cannot carry gold labels or these metadata fields. Opt-in description or combined text may itself contain personal text; the user decides whether to enable it.
9. **Prompt conditions:** few-shot remains the default; `--zero-shot` omits demonstrations. Corrected v1 prompts preserve the complete Figure 3 task paragraph, original order, examples and explanations, with PDF line wraps normalised. The current Chat prompts use the native `relevant`/`not relevant` choice names, sends the instruction-only prompt file as a developer message, and sends `Advert.text()` as a separate user message; native instructions substitute existing relevant/not relevant choices and keep evidence separate. No extra prompt-injection instruction is added. Message roles are not established by the paper. The obsolete legacy filename is removed. The role-split v0 files have new hashes; earlier Chat results remain distinct in the cache and reports. No prompt changes depend on scored results.
10. **Label codes:** current Chat prompts request exact `relevant` or `not relevant` output, mapped to 1/0. Earlier Chat runs used A=relevant and B=not relevant. Each output supplies one binary decision per advert, encoded as 1/0 for metrics. This encoding is not a relevance probability or ranking score.
11. **Chat readout:** the active Chat arm requests no logprobs and plots only its chosen-label FPR/recall point. An earlier 499-row attempt received exact A/B labels but both required label logprobs for only 10 rows; its original incomplete manifest and cache remain historical records. The new binary method was chosen because of this score-coverage limitation, without changing policy, examples, labels, or thresholds in response to performance.
12. **Native probabilities:** read the labelled distribution, not the separate confidence field or winning-choice confidence. Require exactly two valid probabilities summing to one within 1e-4. Do not recalibrate on test labels.
13. **Local decision models:** use d3's verified System One server and Perplexity's evaluated native readout. No universal OpenAI chat facade is invented. Model installation, checkpoint pinning, GPU capacity and access are the user's deployment steps; code never downloads large weights automatically.
14. **API verification:** request/response formats and quoted prices were checked on primary sources as of 13 October 2026 (see docs/SOURCES.md). Current Jev billing and a hosted Perplexity contract remain unknown. Microsoft deployment endpoint/name and local checkpoints remain TODO. Unverified fields block live calls when necessary.
15. **Currency/prices:** USD list prices, no implicit GBP conversion. Price null always means unknown, never zero. Fake explicitly has zero cost. Local/precomputed scores have unknown infrastructure/original-inference cost; zero external API spend is a separate fact, not a reported zero total cost. No regional, long-context, cached-token discount or service-tier adjustments are inferred.
16. **Ceiling:** default USD 0. All billable adapters require known input and output prices before dispatch. The ceiling covers all historical and new external spend in the selected cache directory, across arms/configs; this conservative lifetime scope prevents budget resets on resume. Start a new cache only intentionally. Every concurrent batch reserves all its calls before dispatch.
17. **Token estimates:** dry run uses UTF-8 bytes plus 2,048 input framing tokens, the configured 32-token Chat completion cap (including hidden reasoning), zero output tokens for OpenAI Decisions, and a 4,096-token structural output reserve for System One APIs. It is deliberately conservative and labelled an estimate, not exact tokenisation. Unsupported extra decoding settings and inputs above the model config's `max_input_bound_tokens` are rejected in dry and live runs; the default is 16,384. OpenRouter Microsoft Decision-1 uses its listed 32,768-token context limit so the full title-plus-description validation set passes the input-size check without altering advert text. Correct provider billing and the configured prices are prerequisites to any client-side ceiling; an unexpected provider overrun is saved and stops further calls. No client can undo an already-billed response.
18. **Cache:** key is model config hash (including text fields and precomputed source hash), prompt hash and advert ID. Private entries also retain an input fingerprint and response. The cache lock is local POSIX (macOS/Linux), not a distributed or Windows lock. Atomic writes plus in-flight markers prohibit automatic replay after uncertain outcomes. Cached failures/refusals are also never retried automatically. Review raw responses and provider billing manually before reconciling uncertain entries; deleting cache files may cause charges again. Explicit user authorisation can permit a future retry of an uncertain nonbillable loopback System One call: `retry_authorized_local` retains the entire original entry, time and reason in `retry_authorization`. The runner checks request identity and local/nonbillable constraints; paid/remote calls and unauthorised uncertainty remain blocked. Dry runs do not consume the authorisation. This does not recover the original prediction or measure its unknown resources.
19. **Failure reporting:** the `review_on_failure` screening policy was introduced on 19 October 2026 after observing an animal Luna refusal. Valid predictions use the fixed 0.5 rule; every explicit inference failure is always reviewed. Metrics use every original gold label, with no probability imputation or complete-case exclusion. Coverage is valid predictions / all adverts. ROC curves start at failures-only FPR/recall and sweep genuine scores with ties; binary and all-failure arms have one point. Datasets without either gold class cannot define both ROC axes. Missing/corrupt records and aborted snapshots remain unevaluable; missing billed usage and uncertain calls still stop execution. Historical raw snapshots/cache entries retain their original contents and statuses.
20. **Metrics:** probability arms use score >=0.5; binary Chat uses its chosen relevance labels (encoded 1/0 in the shared metric helper). Positive label is the resolved relevant value. Weighted metrics include both classes weighted by gold support; weighted recall equals accuracy. Undefined precision/F1 is zero (sklearn convention); recall/recall CI with no positives is unknown and no curve is drawn.
21. **Uncertainty:** 95% Wilson interval for measured recall, conditional on this test file and independent adverts. It does not capture annotator uncertainty, related adverts, source drift or model-selection uncertainty. Published rounded aggregates lack sufficient evidence for missed counts, integer confusion matrices or recall CIs, so these remain unknown.
22. **Published numbers:** use LTS-text F1 0.872 from Table 2, record 0.873 from Table 5. Preserve the supplied published values rather than reinterpreting all as weighted or positive-class. Separate published P/R/F1 columns avoid a false claim of known averaging.
23. **Published FPR:** calculate `R * local positives * (1 / P - 1) / local negatives` without rounding inferred counts, and draw/report explicitly conditional values. Their averaging convention, identical test-file version and compatible prevalence are unverified; do not represent these as measured FPR. GPT-4 has only F1, so its FPR is unknown and it is omitted from the figure.
24. **Provenance label:** trained published classifiers are marked as developed with validation data. GPT-4 tuning is unestablished and its row is labelled separately; the previous blanket wording was misleading.
25. **Curves:** show every unique score cutoff with ties reviewed together and explicit failures-only/all-review endpoints (zero origin only when there are no failures), plus expected random-review diagonal and 95%-recall reference. The 95% line is not a selected operating point. No Table 2 claim, cross-fitting or threshold tuning in the current study.
26. **Anchor:** GPT-6 Luna Chat is the measured LLM anchor beside GPT-6 Luna Decisions. Both use the same named model, but the API, prompt format and score type differ; identical internal inference is not established. Chat uses reasoning effort none and a bounded completion for an exact relevant/not relevant binary decision. Its point has no probability cutoff; decision models retain native probability curves and the fixed 0.5 metric cutoff. The paper's GPT-4 F1 remains a historical published aggregate, not a reproduction target. Figure 3 and §3.4 describe few-shot pseudo-labelling, but §4.3 calls Table 5 zero-shot and §3.4 also calls Figure 3 zero-shot; the exact baseline prompt remains ambiguous.
27. **Manifests:** record UTC timestamps (unambiguous), per-arm config/prompt/data hashes, all-score resource totals and separate newly charged-call totals. Unknown resource totals are null, with a known subtotal and unknown count. The current Git commit is recorded when available; a manifest does not capture uncommitted changes. The initial durable manifest uses the final task-aware cache fingerprint, so an abrupt exit cannot leave a temporary configuration identity. Campaign indexing errors during failure cleanup are secondary warnings and never replace the primary failure or interrupt. Historical interrupted manifests and uncertain cache records remain unchanged and do not authorise replay.
28. **Release contents:** the dataset inventory lists the exact tracked study files. The 28 released score snapshots retain measurements and generic failure indicators. Original provider responses, inspections, caches, and additional user-supplied datasets stay local. The two LTS validation CSVs are redistributed unchanged from the public upstream repository, including its seller and location columns; altering them would invalidate the recorded dataset hashes. Scorers never receive those columns. Upstream reuse terms have not been confirmed, so check them before making this repository public.
29. **Tooling:** pip plus pyproject.toml is the supported minimal setup, with ruff/pytest and optional strict mypy. Core targets Python 3.11+; the Perplexity deployment needs 3.12+ separately. No database, UI, framework or unnecessary GPU dependencies in the base environment. The bundled interpreter does not process the editable-install path file here, so the tested setup uses an ordinary wheel install; source development can use PYTHONPATH=src.

30. **Condition provenance:** manifests and reports record condition, example count, prompt version and hash. CLI output directories separate conditions; explicit prompt paths add a hash suffix. Existing configuration fingerprints and cumulative cache budgets remain unchanged. Demonstrations enter the full input estimate. Exact title overlap is checked locally with case/whitespace normalisation; matches never alter the evaluation denominator. This does not rule out near-duplicates.

31. **Family-specific v0 prompts:** the instruction-only LLM text is frozen in separate few-shot and zero-shot files with the current relevant/not relevant choice names. Native v0 YAML retains the five source examples and explanations. The researcher revised the shark criteria to carry the Figure 3 task wording and reports completing manual review of the shark Chat/native analogy. The researcher also confirmed the animal and leather v0 prompts are as intended on 19 October 2026. These are research judgements, not software certifications; the leather label-policy scope remains unresolved. Prompt family/version/hash are attributed per arm; earlier prompt revisions remain distinct. Fake/imported arms are associated with the selected condition but send no prompt.
32. **Prompt selection:** `--llm-prompt` and `--decision-prompt` replace the ambiguous shared `--prompt` override. Both families default to v0, with `--zero-shot` selecting the matching v0 pair. Decision v1 is available only via `--decision-prompt` and has not been evaluated. Overrides must match family and condition. The cache key uses the selected file hash for each arm, while the spend ceiling remains cumulative across the shared cache. `--preview-request` renders one Chat request offline without touching the cache; an aborted payload build is recorded as `cancelled_before_send`, while possible post-dispatch losses remain `in_flight`.
33. **Decision v1 design:** one direct native choice question carries the task. Choice descriptions separate included real shark/ray/chimaera products from other animals, representations, synthetic products, fossils and single teeth. Few-shot v1 retains the published five titles and labels but rewrites the explanations concisely. This pre-evaluation candidate follows provider choice-question guidance; its effect on model performance is unknown and it must not be adjusted using evaluation results.
34. **Prompt layout:** active prompt files and the Figure 3 transcription live under `prompts/sharks/`; the two obsolete shared `sharks_*_v1.yaml` files were removed. Git history retains them. File content hashes, version metadata, default v0 selection and cumulative cache spending are unchanged by the move.

35. **Additional validation files:** `validation_animals.csv` has 499 rows, 101 numeric `1` values and only five populated `relevant` values, all supporting `1=positive`. `leather_validation.csv` has 500 rows, 218 numeric `1` values and no `relevant` column. Title keyword audits of leather positives include non-leather categories; these are signals to review, not grounds for relabelling. `GPT_label` is a separate incomplete model field, never gold. Preserve every row and the original numeric labels.
36. **Manual label review:** label meaning and prompt alignment are researcher judgements recorded privately and summarised in the report. New animal/leather runs and reports require no JSON declaration. Their task definitions propose `1=relevant`, subject to manual confirmation before live runs; this is not certification of review or label quality. Sharks retains semantic inference; new runs record the resolved polarity and CSV hash. Optional historical review files retain task/hash/evidence validation and old report selections must keep matching review paths. Incompatible frozen campaigns require a new campaign, preserving original records and cache accounting.
37. **Task prompts:** additional v0 files under `prompts/animals/` and `prompts/leather/` use Figure 3's task criteria and examples. Chat now uses the same named choices as native decisions; native choice YAML retains the same examples. Minor typo and spacing normalization and the paper's duplicated animal-example numbering are documented in `docs/SOURCES.md`. The original task criteria and examples were selected without tuning on validation scores. Choice names were aligned after earlier runs to remove an avoidable wording difference; new prompt hashes require fresh comparison results. The fifth leather example has no source explanation, so none is invented.
38. **Task comparisons:** published files are task-specific and each holds the same five model categories. Text-image ACTL/LTS rows are labelled as a different modality and shown as conditional square points; text rows use crosses, with color shared by model family. Overridden/synthetic data have no automatic published comparison. Baseline task mismatch fails. Measured costs and summed request latency stay separate from historical published cost claims and wall-clock time.
39. **Identity:** existing cache keys are preserved. Animal/leather output paths include task and their cache configuration hashes include task identity. Manifests and reports record task, source-file hash, prompt hash and review hash where applicable. Review edits alone do not force a second model call for unchanged advert evidence; the cache remains guarded by task, prompt, configuration and text fingerprint.
40. **Output layout:** the default report root is `outputs/comparison`, with paid and local-model checks preserved privately under `outputs/records/`, `outputs/microsoft-decision1-description-v0/` and `outputs/d3-local/`. Disposable Fake/verification outputs may be removed after checking they contain no billable records. `outputs/cache` remains the cumulative spend ledger and must not be reset for tidiness.
41. **Check routing:** an explicit `--output` wins. Otherwise `--check` and `--dry-run` write under `outputs/checks`; ordinary live runs write under `outputs/comparison`. Routing changes neither cache identity nor the shared default `outputs/cache` budget ledger. A live `--check` can still incur charges, and its records must not be deleted automatically.
42. **Dataset-version routing:** new default outputs append task slug, full source-CSV SHA-256, input condition and prompt condition beneath the check/comparison root. Explicit `--output` retains its older layout for compatibility. Existing private records and cache entries are not moved; report pins may refer to those older manifests.
43. **Interactive report selection:** the offline HTML report creates tabs and plots only for dataset versions with at least one active manifest pin in the report selection file. Saved runs, commented pins and dataset settings alone create no tabs; discovery remains a separate `site/build.py discover` operation. Its default visible series are presentation settings, not model selection, score exclusions, prompt tuning or operating-threshold choices. It reports full-denominator review-on-failure policy metrics and coverage for finished arms, embeds aggregate coordinates only, and displays published text and text-image P/R as conditional ROC points with distinct markers and shared family colors. F1-only GPT-4 cannot be placed on the ROC plot and has unknown table FPR. The comparison table displays GPT-4 as few-shot by researcher assumption, while preserving the source name “GPT-4 zero-shot” and explicitly stating that its exact shot condition is unverified. Table boldface marks available numeric column leaders across finished measured-policy and published rows, without asserting comparability or significance; published missed counts and N/A values never compete. The displayed API cost per advert divides known recorded total API cost by the full dataset size, without changing cache or spending accounting. Local d3 is marked Free and counted as zero **external API** cost when its validated configuration is nonbillable and loopback; its infrastructure cost remains unknown. Finished arms with failures retain a model-name marker and valid/total coverage in the table.
44. **Resource panel:** the HTML report plots per-advert recorded API charge and saved request latency only for completed, pinned arms with real inference requests. It uses the full dataset denominator, includes all such arms regardless of ROC-plot visibility, and leaves unavailable values unknown. Validated local loopback inference has zero external API charge but unknown hardware, electricity and infrastructure cost. Published full-collection cost claims have a different scope and are not charted beside current per-request values. Synthetic, imported and aborted records are omitted; finished arms with failures retain all recorded costs and timings.
45. **Reviewed factorial campaigns:** the new script selects one task and explicit prompt version, audits each adapter's rendered prompt and allowlisted advert evidence offline, and requires a clean committed revision for live calls. Shared native content and evidence equality are software checks; equivalence of the Chat policy wording is a human research judgement. Exact cache matches may be reused, with new manifests and scores stored under one private campaign directory. A selection candidate is created only after full coverage; no HTML preview is generated. The active report selection changes only through an explicit import or edit. Sharks has 16 declared arms. Animals and leather each have eight title-only arms, declared centrally in task definitions. Animal descriptions (10 of 499 rows) are excluded based on availability before evaluation; leather has no description column. Explicit lower-level description runs remain separate experimental conditions. The GPT-6 Luna Chat conservative input guard is 32,768 for full description requests; this configuration change deliberately produces a new cache fingerprint.

46. **Campaign continuation:** CLI exit 2 means every requested arm has full result records with explicit inference failures; the factorial launcher validates new snapshot identities, provenance, row coverage and billed usage before continuing. Exit 1, interruption, missing records, budget/accounting errors and uncertain calls remain fatal. Candidates include every finished arm, with failures disclosed. No automatic retry is added. Frozen Git-audit resume checks remain strict; changed code requires a new campaign that reuses the existing cache, never a rewritten audit.

47. **Birds composite preparation:** the researcher explicitly authorised deriving relevance from the three source exclusion labels: any `1` is irrelevant; all `0` is relevant; otherwise unresolved. Retain every source row and label unchanged. Only the 16,407 determinable rows enter the derived evaluation CSV; preserve the 102 unresolved rows separately and disclose both denominators. No model-derived adjudication or performance-based exclusion is used. The source has 9,640 derived positives and 6,767 derived negatives. The authors' README appears to transpose label1/label2 relative to paper counts; the symmetric composite rule is unaffected. These labels do not establish illegality or annotation correctness.
48. **Combined-column input:** `--combined-text` is an explicit opt-in to the existing `title_and_desc` column, including description content. It uses one advert-text evidence field, independently of the historical separate-column title-plus-description mode. Manifests, cache fingerprints and output routing preserve `combined_text` as a loading key; reports label it title + desc, matching separate-column title/description coverage; title-only defaults and historical payload/cache hashes are preserved. Preparation maps birds `all_text_raw` directly, without attempting to split title from description. This input support introduces no bird task, supervised baseline or live campaign; the separately added bird prompts are described below.

49. **Bird zero-shot prompts:** the Chat/native v0 pair in `prompts/birds/` uses identical prediction criteria and exclusions, without demonstrations. Relevant means an offer of live birds for sale, exchange or free transfer that is neither wanted/request nor an offer of Anseriformes, Galliformes or domestic pigeons. These taxonomic exclusions apply regardless of wild/domestic wording; eggs, products and accessories alone are not live birds. Any exclusion wins, matching the composite target. This is the researcher's derived policy, not a reproduction of a published composite classifier or certification of label alignment. Birds is registered separately as a zero-shot-only combined-text task; no performance results informed these prompts.

50. **Bird task integration and compatibility:** birds defaults to the processed CSV and positive polarity `1`, has no published composite baseline and declares one combined-text/zero-shot condition across the existing four models. Direct CLI runs require explicit `--combined-text --zero-shot`; the campaign passes both from its task definition. Other tasks retain both shot conditions, their old inputs and unchanged audit dictionaries. Historical cache identities, manifests, review records and pins require no migration. Resume continues to require the exact frozen Git audit; changed revisions require new campaigns reusing unchanged requests. No calibration, threshold tuning, concurrency change or automatic report-pin activation is introduced.


51. **Runtime optimisation:** model arms stay sequential; per-arm request concurrency is runtime provenance, not a changed prediction/input condition or cache namespace. A persistent thread pool refills as responses finish and preserves source order in saved scores. Under the exclusive shared cache lock, starting charges are read once, each dispatch reserves its conservative upper cost, each completion replaces that reservation with its accounted charge, and the durable cache is rescanned when submitted work drains. Admission stops on budget/accounting problems or uncertainty, while outstanding work is retained. Default research behavior for explicit inference failures is unchanged; timing checks can opt into stop-on-error. Invented runtime fixtures and separate IDs isolate throughput selection from evaluation accuracy. Timing recommendations use median throughput and a 10% gain requirement; d3 memory/swap checks remain a separate acceptance condition. Benchmark spending shares the existing ledger and is capped at USD 1 additional and USD 15 cumulative. Request latency, fresh scoring throughput and invocation wall time are reported separately; invented-input estimates do not establish real-dataset speedups.
